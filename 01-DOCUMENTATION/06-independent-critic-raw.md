**6.1 Core Principle**

**The critic judges outcomes, not intentions.**

The builder may believe:

&ldquo;This looks premium.&rdquo;

The critic doesn't care what the builder intended.

It asks:

**&ldquo;What does the rendered website actually communicate?&rdquo;**

This is especially important because the same underlying technical
system can produce very different visual outcomes depending on token
application, composition, hierarchy and imagery. The research
specifically advocates dynamic application of design tokens, layout
sequences and typographic scales to create visually distinct websites.

**6.2 Independent Means Independent in Role**

Even when the same model is used, the critic receives a **different
system prompt and evaluation framework**.

The roles are:

Builder

&rarr; "Create this."

Critic

&rarr; "Prove whether this is good."

Refiner

&rarr; "Fix what the critic proves is weak."

The critic must be comfortable saying:

**The implementation is wrong.**

and also:

**The blueprint itself needs reconsideration.**

That is a key improvement.

**6.5 Two Evaluation Modes**

This is an important improvement.

The critic needs:

**Mode A &mdash; Blueprint Fidelity**

Did the implementation preserve the intended design?

and:

**Mode B &mdash; Outcome Quality**

Is the resulting website actually good?

These are not the same.

Example:

Blueprint quality = excellent

Implementation fidelity = excellent

Outcome quality = poor

Then the critic should identify that **the problem originated in the
blueprint**.

Conversely:

Blueprint = excellent

Implementation fidelity = poor

Outcome = mediocre

Then the builder is the problem.

**6.16 Critic Must Diagnose ROOT CAUSE**

This is a major improvement.

Don't say:

&ldquo;Hero looks weak.&rdquo;

Instead classify:

Problem:

Hero feels generic.

Root cause:

Implementation drift.

Evidence:

Blueprint specified asymmetric editorial composition,

but rendered result uses centered alignment.

Correction:

Restore offset composition.

Possible root causes:

Blueprint problem

Implementation problem

Content problem

Asset problem

Typography problem

Responsive problem

Conversion problem

Technical problem

**6.17 Evidence-Based Criticism**

Every major criticism must include evidence.

Example:

Observation:

Services feel repetitive.

Evidence:

6 visually identical cards with same image ratio,

same heading hierarchy and same spacing.

Impact:

Reduces hierarchy and creates template-like appearance.

Severity:

P1.

Correction:

Convert first service into dominant feature,

remaining services into secondary index.

That is much more actionable than:

&ldquo;Make services more creative.&rdquo;

**6.18 Visual Observation vs Opinion**

The critic must distinguish:

**Observation**

&ldquo;Six cards have identical size and structure.&rdquo;

**Interpretation**

&ldquo;This reduces hierarchy.&rdquo;

**Recommendation**

&ldquo;Use unequal composition.&rdquo;

This makes the critic more objective.

**6.19 Severity System**

Use:

**P0 &mdash; Ship Blocker**

- broken booking

- inaccessible critical interaction

- broken mobile

- unusable CTA

**P1 &mdash; Major**

- generic visual structure

- significant conversion issue

- strong brand mismatch

- major blueprint drift

**P2 &mdash; Moderate**

- spacing

- typography

- crop

- rhythm issue

**P3 &mdash; Polish**

- micro-interaction

- subtle alignment

- minor visual refinement

**6.27 Quiet Zone Test**

Check whether the page has enough restraint.

Without quiet zones:

everything screams.

With too many:

The critic should judge the balance.

**6.29 AI-Generic Risk**

**6.30 Template Risk**

Separate from AI risk.

Ask:

Could another client's logo, colors and text be inserted here and
produce essentially the same website?

If yes:

**FAIL**

This directly addresses the original problem you raised when we started
building this system.

**6.31 Competitive Differentiation Test**

Compare the rendered website against competitors.

Ask:

**Does this business look meaningfully different from its local
competitors without becoming inappropriate for the category?**

This makes the critic aware of the business's actual market.

**6.32 Category Familiarity Test**

Creative differentiation should not create confusion.

Ask:

This produces a useful balance:

Category familiarity

\+

Creative differentiation

**6.42 "Premium" Is Not Enough**

The critic should distinguish:

**Polished**

Clean, neat, professional.

**Premium**

Sophisticated, intentional, refined.

**Creative**

Distinctive, memorable, art-directed.

A site can be:

polished = 10

premium = 8

creative = 4

and still fail the Blogspage standard.

**6.43 Blogspage Signature Standard**

The final critic should ask:

**Would this website improve Blogspage AI's portfolio?**

A website that is technically excellent but generic should not be
considered a showcase piece.

**6.49 Refinement Instructions Must Be Specific**

Bad:

&ldquo;Make the hero more premium.&rdquo;

Good:

&ldquo;Restore the blueprint's asymmetric 7/5 image-text relationship,
move the image 2 columns beyond the main container, reduce CTA count
from two to one, and preserve the editorial whitespace.&rdquo;

This gives the implementation agent actionable instructions.

**6.51 Refinement Regression Protection**

After every correction:

Did we fix the problem?

Did we damage anything else?

Did creative fidelity fall?

Did mobile break?

Did conversion weaken?

This is essential.

**6.53 Evidence of Improvement**

The critic should say:

&ldquo;Version B improved visual hierarchy because the primary service
now occupies approximately 45% of the section rather than six equal
visual units.&rdquo;

Rather than:

&ldquo;Version B looks better.&rdquo;

Stop when:

**6.55 Blueprint Reconsideration**

This is a powerful addition.

The critic may recommend:

Implementation refinement

OR

Blueprint refinement

Example:

Assets cannot support cinematic direction.

Recommendation:

Return to Phase 4 and lower image dominance.

That is better than forcing the implementation agent to solve an
impossible design strategy.

**6.56 Asset Reality Check**

The critic should inspect whether:

selected language

\+

selected composition

actually matches the supplied assets.

The research explicitly says poor imagery should trigger alternative
composition strategies rather than generic stock imagery.

**6.57 Content Reality Check**

Likewise:

Is the design trying to create a visual narrative that the available
business content cannot support?

If yes:

return to Phase 4.

**6.63 Phase 6 Final Principle**

I would make this the official principle:

**The critic's responsibility is not to make every website safer,
cleaner, or more conventional. Its responsibility is to make each
website more appropriate, more intentional, more distinctive, and more
effective.**

That matters for your creativity requirement.

The critic should **not punish creativity simply because it is
unusual**.

It should punish:

**unjustified creativity.**
