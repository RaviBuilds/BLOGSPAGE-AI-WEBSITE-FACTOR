## 2. Seam 1 — the defect and the fix

**The defect.** `failure-routing.md` §2 routes a business-understanding problem and a factual-integrity problem to owning phase "Research" → `RETURN_TO_RESEARCH`, and §5 makes "Is a presented fact wrong, unverified, or fabricated?" the first ordered routing question. But `state-machine.md` §4 gave `RESEARCHING` **no** `RETURN_TO_*` exit, while `RETURN_TO_RESEARCH`'s only exit is `RESEARCHING`. The research correction loop was therefore inoperable: the only state that can *produce* a research failure could not legally reach the one state that *repairs* it.

**The observable consequence.** M2.4 persisted all four research artifacts, evaluated the gate, received the canonical `RETURN_TO_RESEARCH` recommendation from the frozen `FailureRouter`, and then refused it as `ILLEGAL_TRANSITION`. The condition was recorded as a canonical-seam finding in tests rather than patched — correctly.

**The fix.** One edge, in canon and its projection together:

| File | Change |
|---|---|
| `02-CONTROL-PLANE/state-machine.md` | §2 RESEARCHING "Valid next states" and §4 transition table row — add `RETURN_TO_RESEARCH` |
| `runtime/state/TransitionTable.ts` | `buildFixedTransitions()` — add the edge; header counts 64→65 fixed, 69→70 total |
| `runtime/tests/TransitionTable.test.ts` | the `64 fixed rules` count assertion → 65 |
| `runtime/orchestrator/README.md` | the seam was documented as unresolved; now documented as resolved |

**No orchestration logic was added.** The edge alone makes the pre-existing gate-failure routing legal, so `Orchestrator.run()` needed no change for this seam. Production wiring now commits `RESEARCHING → RETURN_TO_RESEARCH` and stops safely (`no-action-for-state`).

**Why no action is registered for `RETURN_TO_RESEARCH`.** Its only legal exit is `→ RESEARCHING`, and corrected facts must come from outside the factory. A `null`-worker loop action would re-run the same deterministic `ResearchWorker` over unchanged input — producing a byte-different artifact that is not a correction, burning versions, then tripping the cycle guard. Leaving it unregistered matches the `NEEDS_*` return-state convention. This is asserted by tests, not assumed.

**Scope proof.** `runtime/tests/orchestrator/Seam1.test.ts` parses `state-machine.md` §4 at test time and compares **every row** against the implementation, so any stray edge in any row fails the build with that row named. It also asserts negative controls: `RESEARCHING` still refuses `DELIVERED`, `APPROVED`, `IMPLEMENTING`, `CRITIQUING`, `REFINING`, `BLUEPRINT_READY`, `CREATIVE_DIRECTION`, `RETURN_TO_BLUEPRINT`; `RETURN_TO_RESEARCH` still refuses everything except `RESEARCHING`; the five dynamic `returnTarget` states and the primary-state return-target rule are unchanged.

## 3. Gate-condition contracts

`02-CONTROL-PLANE/gate-conditions.md` is new. It documents all 27 conditions and the policy:

- **Resolvable: 10** (unchanged) — artifact existence, or re-established integrity plus a schema-guaranteed field.
- **No canonical decision procedure: 17** (unchanged) — 13 semantic judgements, `build_success` (a runtime fact no artifact records), and `creative_input_versions_recorded` (see below).

**Implemented: exactly one.** `creative_design_intent_statement_present` — `04-SCHEMA/creative-direction.schema.json` declares `designIntentStatement` as `{"type":"string","minLength":10}` and lists it in the artifact's root `required` array, so a schema-valid Creative Direction artifact necessarily satisfies it. The field name and minimum length are **read from canon**, not chosen.

**Rejected candidate, recorded.** `composition_complete` was expected to be schema-derivable. `04-SCHEMA/design-blueprint.schema.json` models the Composition Plan's `sections` as an array of bare strings (`"items": {"type":"string"}`, `minItems: 1`) and records no layout, interaction or responsive field. The schema cannot detect the §5.1 violation, so the condition stays unresolved.

**Partial evidence rejected.** `creative_input_versions_recorded` requires that "**every** consumed input" be recorded. Canon proves only "at least one" (`consumedArtifactVersions`, `minItems: 1`). Completeness would require knowing the consumed set independently, and nothing canonical or registered names it. It stays unresolved.

**Implementation shape.** `runtime/orchestrator/coordination/ConditionResolutionContext.ts` — a `ValidationContext` **decorator** that answers only the resolved condition and delegates everything else unchanged, so an unresolved condition still raises `ConditionContractUnresolvedError`. Integrity is re-established first via `validateCurrentArtifact`; a missing, corrupt, foreign or tampered artifact yields `false`, never a vacuous `true`.

**Deliberately unwired.** Nothing constructs the decorator outside its tests, so production condition behaviour and the all-six-gates-fail-closed fact (`runtime/tests/ProductionWiring.test.ts`, **unmodified**) are unchanged. A test asserts that `ProductionValidationContext` still fails closed on the very condition the decorator resolves — proof it is not in the production path.

## 4. Human approval / resume lifecycle

New module `runtime/orchestrator/approval/`:

| File | Responsibility |
|---|---|
| `ApprovalTypes.ts` | gates 1–3, per-gate definitions and canonical rejection routes, record shape, canonical-JSON digest, typed errors |
| `ApprovalWriteLock.ts` | its own `.approval-write.lock`, mirroring the established `ProjectLock`/`ProcessWriteLock` pattern |
| `ApprovalStore.ts` | durable persistence + SHA-256 integrity, reads fail closed |
| `ApprovalCoordinator.ts` | policy: routing, invariants, idempotency, supersession |

**Persistence decision (and why not an artifact).** `human-approval.md` §7 invariant 2 mandates recording every decision. An approval is **not** a 12th artifact: `artifact-envelope.schema.json` declares the `artifactType` enum a closed set ("Closed set of exactly eleven peer artifacts … No thirteenth type is added by a schema"). Storing one as an artifact would also make it indistinguishable from real content on every read path. A dedicated store is used instead, at `{workspaceRoot}/{projectId}/control/approvals/gate-{n}.json` — outside `{projectId}/artifacts/`, which `cleanupTempFiles` scans exclusively, so artifact reconciliation structurally cannot reach it. A test runs a real artifact commit (lock → reconcile → temp cleanup → manifest write) and shows the approval record untouched and not visible as an artifact.

**Records** carry a SHA-256 digest over their canonical JSON minus the digest field, recomputed on every read. An edited decision, reason or identity fails closed with `ApprovalIntegrityError`. Absence returns `null`; corruption is an error, never a silent `null`.

**The six invariants, all satisfied and tested.** Exactly three gates; every decision recorded (with reason on rejection); Gate 3's Critic precondition left to M2.2 rather than duplicated; `isFinalGateUnlocked()` requires Gates 1 and 2 approved; approval never inferred from silence; a reason-less or undiagnosed rejection routes to `NEEDS_HUMAN_REVIEW`.

**Resume.** `Orchestrator.resumeWithApproval(projectId, gate)` completes the gate's transition from an already-recorded decision, through the ordinary `TransitionCoordinator`, so M2.1's WAL, legality check and idempotency all apply. It is decision-driven, never inference-driven: no decision → no movement; wrong state → no movement; illegal route → no movement and reported. Re-recording an identical decision is a no-op; an identical decision with a *different* route or reason is a new, superseding decision.

1. **`artifact-envelope.schema.json` contradicts itself** on the artifact-type count — line 15 says "twelve contracted artifact types", line 87 says "exactly eleven peer artifacts", and the enum has 11 members. No runtime effect; wording should be reconciled.
2. **Four approval rejection routes are canonical but not legal transitions** (`human-approval.md` §4.4/§5.4 vs `state-machine.md` §4): Gate 1 → `NEEDS_CONTENT`, `NEEDS_ASSETS`, `NEEDS_CREDENTIALS`; Gate 2 → `NEEDS_ASSETS`. Recorded in the routes table, reported at runtime as `transitionLegal: false`, never forced. Tests pin all four by name.
3. **17 gate conditions have no canonical decision procedure** — the reason all six gates still fail closed.
4. **`RETURN_TO_RESEARCH` has no registered action and no canonical resume mechanism.** What constitutes "research and business intelligence corrected and revalidated" (`state-machine.md` §2) is unspecified; today its exit re-runs the deterministic worker over unchanged input.
5. **No CLI surface** was added. The capability is orchestrator API only (`recordApproval`, `resumeWithApproval`, `approvals`), fully tested; human-facing entry points are deferred explicitly.
