# M2.3-B Decision Record

**Scope:** the decisions taken in milestone M2.3-B (Seam 1, gate condition contracts, human approval/resume), the evidence behind each, and the canonical gaps this milestone deliberately leaves open.

**Principle applied throughout:** the orchestrator orchestrates only. Where a decision needed a rule, the rule was taken from a canonical document or the work stopped. No canonical rule was invented to make code pass.

## 1. Seam 1 — RESEARCHING → RETURN_TO_RESEARCH

| Aspect | Decision |
|---|---|
| Finding | `failure-routing.md` §2 maps a business-understanding problem and a factual-integrity problem to owning phase "Research" → `RETURN_TO_RESEARCH`, and §5 makes "Is a presented fact wrong, unverified, or fabricated?" the **first** ordered routing question. `state-machine.md` §2 gave `RETURN_TO_RESEARCH` the single exit `RESEARCHING`, but §4 gave `RESEARCHING` **no** `RETURN_TO_*` exit. The research correction loop was therefore inoperable: the only state that can produce a research/factual-integrity failure could not legally reach the one canonical state that repairs it. |
| Consequence before the fix | M2.4 persisted all four research artifacts, evaluated the gate, received the canonical `RETURN_TO_RESEARCH` recommendation from the frozen `FailureRouter`, and then **refused** it as `ILLEGAL_TRANSITION` because no legal edge existed. The condition was recorded as a canonical-seam finding in `runtime/tests/orchestrator/ResearchVerticalSlice.test.ts` and `Orchestrator.test.ts` rather than patched. |
| Canonical evidence | `failure-routing.md` §2 (problem-class table), §5 ordered routing question 1, §6 invalidation table; `state-machine.md` §2 `RETURN_TO_RESEARCH` "Valid next states | RESEARCHING"; §4 `RETURN_TO_RESEARCH → RESEARCHING`. |
| Decision | Add the missing edge `RESEARCHING → RETURN_TO_RESEARCH`. This is the **only** canonical change in this milestone. |
| Files changed | `02-CONTROL-PLANE/state-machine.md` §2 (RESEARCHING "Valid next states") and §4 (transition table row); `runtime/state/TransitionTable.ts` `buildFixedTransitions()` and its rule-count header. |
| Scope control | One edge. No state added, none removed, no other row touched. Verified by a doc↔implementation drift guard that parses `state-machine.md` §4 and compares **every** row against the table (`runtime/tests/orchestrator/Seam1.test.ts`). Rule count 64 → 65 fixed (69 → 70 including the 5 dynamic `returnTarget` rules); `runtime/tests/TransitionTable.test.ts`'s count assertion was updated for the same reason. |
| Orchestration impact | **None.** No orchestration logic was added. The edge alone makes the existing gate-failure routing legal, so `Orchestrator.ts` needed no change for this seam. |
| Resulting behaviour | Production wiring now commits `RESEARCHING → RETURN_TO_RESEARCH` and then stops safely at `RETURN_TO_RESEARCH` (`no-action-for-state`). |
| Why no action is registered for `RETURN_TO_RESEARCH` | Its only legal exit is `→ RESEARCHING`, and the corrected facts must come from outside the factory. Registering a `null`-worker loop action would re-run the same deterministic `ResearchWorker` over unchanged input, producing a byte-different artifact that is not a correction, burning versions, then stopping at the cycle guard. Leaving it unregistered matches the `NEEDS_*` return-state convention: the human/future milestone that supplies the corrected facts resumes it. Asserted, not assumed (`Seam1` / `ResearchVerticalSlice` tests). |

| Aspect | Decision |
|---|---|

The field name and minimum length are read from canon, not chosen. |

## 3. How approval records are persisted (and why not as an artifact)

| Aspect | Decision |
|---|---|
| Requirement | `human-approval.md` §7 invariant 2: "Every approval and rejection is recorded, with the reason on rejection." Persistence is mandatory. |
| Rejected option — a 12th artifact type | `04-SCHEMA/_common/artifact-envelope.schema.json` declares the `definitions.artifactType` enum a **closed** set: "Closed set of exactly eleven peer artifacts ... No thirteenth type is added by a schema and none is introduced by a project run." Adding `HUMAN_APPROVAL` would require editing the frozen `runtime/artifacts/ArtifactTypes.ts`, the canonical envelope enum and a new `04-SCHEMA` file — three canon changes beyond Seam 1, plus the side effect that a stored approval would be **indistinguishable** from real content on every read path (e.g. `hasArtifact(REFINEMENT_PLAN)` returning true for a project with no refinement plan). Rejected. |
| Rejected option — reuse an existing artifact type as a carrier | Also rejected, for a mechanical reason worth recording: `ArtifactRepository.saveArtifact` **overwrites** the document's identity with the caller's artifact type and then validates it against that type's schema unconditionally. An approval record stored "as" a Refinement Plan would be schema-rejected (its `required` payload fields cannot be satisfied honestly) or, if forced through an open sub-object, would amount to fabricating a plausible Refinement Plan in order to hide an approval inside it. Rejected as data laundering. |
| **Decision** | A dedicated orchestrator-surface store: `{workspaceRoot}/{projectId}/control/approvals/gate-{1|2|3}.json`, implemented by `runtime/orchestrator/approval/ApprovalStore.ts`. |
| Containment | Artifacts live at `{projectId}/artifacts/…` and `ArtifactRepository.cleanupTempFiles` scans only that directory, so `{projectId}/control/` is structurally invisible to artifact reconciliation — proven by a test that runs a real artifact commit (lock, reconcile, temp cleanup, manifest write) and shows the approval record untouched and not visible as an artifact. |
| Integrity | Records are committed with the M2.3-A `durableWrite` helper (temp → fsync → rename) and carry a SHA-256 digest over their canonical JSON minus the digest field. Every read recomputes it, so any post-commit edit fails closed with `ApprovalIntegrityError`. Absence returns `null`; corruption is an error, never a silent `null`. |
| Project isolation | `validateProjectId` and `assertPathInsideWorkspace` are imported **unmodified** from `artifacts/validateProjectId.ts`, so approval paths inherit the exact HIGH-1 guarantees of artifact paths. |
| Locking | A dedicated `ApprovalWriteLock` with its own lock file (`.approval-write.lock`), mirroring the established `ProjectLock` / `ProcessWriteLock` pattern. The artifact lock is frozen and hardcodes `.artifact-write.lock`; sharing it would couple two independent concerns, and `ProcessWriteLock` itself documents this same reasoning for `state/ProjectLock.ts`. |

Recorded, **not patched**, and asserted as reported-but-not-forced.

| 1 | `NEEDS_ASSETS` ("Assets are missing or insufficient") | `RESEARCH_READY` | **No** — same row |

| 2 | `NEEDS_ASSETS` ("Direction requires assets that do not exist") | `BLUEPRINT_READY` | **No** — §4 gives `BLUEPRINT_READY` → `IMPLEMENTING, RETURN_TO_BLUEPRINT, RETURN_TO_RESEARCH, NEEDS_HUMAN_REVIEW, BLOCKED` |
| 1, 2, 3 | `NEEDS_HUMAN_REVIEW` ("Reason not stated") | — | Yes |
| 2 | `RETURN_TO_BLUEPRINT`, `RETURN_TO_RESEARCH` | `BLUEPRINT_READY` | Yes |

**Why this was not fixed.** Adding four edges to `state-machine.md` §4 and `TransitionTable.ts` is a larger canonical change than Seam 1 and is not implied by the failure-routing canon. It is a factory-level decision (either the state machine gains these routes, or the approval tables are narrowed), and per `failure-routing.md` §1 rule 6 an unclear question is routed to human review rather than guessed at.

**Behaviour instead.** The coordinator records the canonical route faithfully (invariant 2), reports `transitionLegal: false`, and `resumeWithApproval` returns `transitioned: false` with a reason. The project does not move; the transition is never forced. Tests pin all four cases by name.

## 5. Human approval lifecycle — ownership and invariants

| Invariant (`human-approval.md` §7) | How it is satisfied |
|---|---|
| 1 — exactly three gates, no additional gates per project | `HUMAN_APPROVAL_GATES = [1,2,3]`; any other gate number is refused by both the store and the coordinator. |
| 2 — every approval and rejection recorded, with reason on rejection | Every decision is persisted. A reason-less rejection is still recorded, with its route set to `NEEDS_HUMAN_REVIEW`. Re-deciding a gate preserves the superseded decision in `supersedes` rather than overwriting history. |
| 3 — Gate 3 requires a passing Critic Validation | **Not re-implemented here, by design.** It is a gate condition (`critic_verdict_ship` etc.) owned by M2.2 and evaluated by the orchestrator as the Final Approval gate. Duplicating it would create a second source of truth for a gate predicate. Recorded as a pointer, not a copy. |
| 4 — Gate 1 and Gate 2 approvals are preconditions for final approval | `ApprovalCoordinator.isFinalGateUnlocked()` requires both records to be `APPROVED`. |
| 5 — approval is never inferred from silence or absence of objection | `read()` returns `null` for an absent record; `run()` still stops at every human-stop state; `resumeWithApproval` refuses to move when no decision exists. |
| 6 — a rejection without a stated reason routes to `NEEDS_HUMAN_REVIEW` | Both a blank reason and a stated-but-undiagnosed reason resolve to `NEEDS_HUMAN_REVIEW`, per `failure-routing.md` §1 rule 6. |

**Identity and idempotency.** A decision must name its approver (`decidedBy`); approval is never anonymous. Re-recording an identical decision is a no-op that returns the existing record and rewrites nothing. An identical *decision* with a different rejection route or reason is a **new** decision (superseding), not a no-op — the check compares route and reason as well.

**Who performs the transition.** The coordinator never transitions state. `Orchestrator.resumeWithApproval` completes the gate's transition through the ordinary `TransitionCoordinator`, so M2.1's WAL, legality check and idempotency all still apply. This is the resume path past a human-stop state. `types.ts` already anticipated it: *"Resume after a NEEDS_* state is performed by the human (or a future milestone) ... the orchestrator never invents an approval of its own."*

No CLI command surface was added in M2.3-B. The capability is exposed as orchestrator API (`recordApproval`, `resumeWithApproval`, `approvals`) and is fully tested, but human-facing entry points (argument parsing, operator identity, interactive prompts) are a separate concern that no canonical document in this milestone's scope specifies. Deferred explicitly rather than approximated.

## 7. Canonical gaps recorded (not fixed)

1. **`artifact-envelope.schema.json` contradicts itself on the artifact-type count.** Line 15 says *"Which of the twelve contracted artifact types this is"* while line 87 says *"Closed set of exactly eleven peer artifacts"*. The `definitions.artifactType` enum has exactly 11 members, and `runtime/artifacts/ArtifactTypes.ts` cites "exactly eleven". No runtime effect, but the canonical wording should be reconciled.
2. **The four approval rejection routes of §4** above.
3. **The 17 gate conditions** with no canonical decision procedure (`gate-conditions.md` §3).
4. **`RETURN_TO_RESEARCH` has no registered action and no canonical resume mechanism.** Its exit is `RESEARCHING`, which re-runs the deterministic research worker over unchanged input. What actually constitutes "research and business intelligence corrected and revalidated" (`state-machine.md` §2) is not specified by any canonical document.
