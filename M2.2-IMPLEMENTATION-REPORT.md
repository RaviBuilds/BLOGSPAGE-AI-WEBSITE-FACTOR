## Architecture

### M2.2 Design Principles

M2.2 is a **pure gate evaluation and routing layer**:

- **No State Mutation**: M2.2 does not mutate project state
- **No Persistence**: M2.2 does not persist artifacts or approvals
- **No Orchestration**: M2.2 does not orchestrate workflow
- **Pure Functions**: FailureRouter and all checks are pure
- **Stateless Evaluation**: GateEvaluator is stateless

### M2.1 Isolation

**Verified Architectural Separation**:
- M2.1 does not depend on M2.2
- M2.2 does not invoke M2.1 state mutation or persistence components
- M2.2 only minimally references the M2.1 State enum where required by the gate register
- Static architectural isolation verified through dependency analysis

### Human Approval Points

The three canonical human approval points per quality-gates.md:

1. **After Research Validation** (Gate 1) - Human reviews Business Intelligence
2. **After Blueprint Validation** (Gate 3) - Human reviews Technical Design
3. **At Final Approval** (Gate 6) - Human provides final sign-off

**Note**: M2.2 evaluates approval requirements but does not persist approval decisions. Approval persistence is a future M2.3/M2.4 responsibility.

### Failure Routing

**All 12 canonical problem classes are handled**:
- CONTENT_PROBLEM → NEEDS_CONTENT
- ASSET_PROBLEM → NEEDS_ASSETS
- CREDENTIALS_PROBLEM → NEEDS_CREDENTIALS
- BUSINESS_UNDERSTANDING_PROBLEM → RETURN_TO_RESEARCH
- FACTUAL_INTEGRITY_PROBLEM → RETURN_TO_RESEARCH
- CREATIVE_STRATEGY_PROBLEM → RETURN_TO_BLUEPRINT
- STRUCTURAL_DESIGN_PROBLEM → RETURN_TO_BLUEPRINT
- IMPLEMENTATION_QUALITY_PROBLEM → RETURN_TO_IMPLEMENTATION
- UNMET_REQUIREMENTS_PROBLEM → RETURN_TO_IMPLEMENTATION
- CRITIC_MISALIGNMENT → CRITIC_REVIEW
- APPROVAL_CRITERIA_UNMET → HUMAN_REVIEW
- **UNCLEAR → NEEDS_HUMAN_REVIEW** (per failure-routing.md §3.12)
